## დასკვნა და შემოწმების საზღვრები

კოდში დადასტურდა რამდენიმე დამოუკიდებელი პრობლემა: ისტორიის გვერდზე კონფიგურაციის დაკარგვა, დიდი ანგარიშების მეხსიერებაში მთლიანად ჩატვირთვა, ერთდროულ შეკვეთებში არასაკმარისი ტრანზაქციები, ბაზის ბლოკირების ხანგრძლივი ლოდინის შესაძლებლობა და არასაკმარისი დიაგნოსტიკა. შესაბამისი ცვლილებები და განმეორებადი ტესტები ამავე განშტოებაშია.

**კონკრეტულად თქვენს ჰოსტინგზე ხუთი დღის შემდეგ დაწყებული 20-წამიანი დაყოვნების სრული მიზეზი ჯერ არ არის დადასტურებული.** საწყისი აუდიტი რეპოზიტორიასა და იზოლირებულ ბაზაზე ჩატარდა. შემდგომ ჰოსტინგზე წვდომით დადასტურდა ისტორიის რეალური SQL შეცდომა, ხუთი გამოტოვებული ინდექსი და OPcache-ის განმეორებადი გაფრთხილება. შესრულებული სამუშაო და დარჩენილი შემოწმებები ქვემოთაა აღწერილი; მრავალდღიანი დატვირთვის დაკვირვება ჯერ არ ჩატარებულა.

ფოტოების არქონა თავისთავად სწრაფ პასუხს არ უზრუნველყოფს: პატარა მოთხოვნამაც შეიძლება რიგში, PHP-ის სესიაზე ან ბაზის ბლოკირებაზე დიდხანს მოიცადოს. ყოველდღიური გადატვირთვა ან timeout-ის გაზრდა მიზეზის დადგენას ვერ ჩაანაცვლებს.

## გაზომვა და ტესტები

იზოლირებული გარემო: PHP 8.3, MariaDB 10.11, სინთეზური მონაცემები. გამოყენებული იყო ახალი ცარიელი `pos_test`; წარმოების მონაცემები და კონფიგურაცია არ გამოყენებულა. ტესტი არსებულ ბაზას არ ასუფთავებს.

სცენარი ამატებს 10 000 შეკვეთას და 100 000 პოზიციას არსებულ სატესტო ჩანაწერებს. ძველი და ახალი სტატისტიკა ეშვება ერთსა და იმავე ბაზასა და პერიოდზე. ბოლო გაშვების შედეგი:

| მეტრიკა | საწყისი სტატისტიკა | განახლებული სტატისტიკა |
|---|---:|---:|
| სამი გაზომვა, ms | 268.2 / 361.3 / 389.3 | 162.1 / 177.2 / 197.3 |
| მედიანა, ms | 361.3 | 177.2 |
| PHP პიკური მეხსიერება, MiB | 70.0 | 2.0 |

ამ სცენარში ანგარიში დაახლოებით **2-ჯერ სწრაფია** და **35-ჯერ ნაკლებ PHP მეხსიერებას** იყენებს. ეს არ არის რეალური ჰოსტინგის სიჩქარის გარანტია ან ხუთდღიანი უწყვეტი დატვირთვის ტესტი. სცენარში განსხვავებული პროდუქტების რაოდენობა მცირეა. დიდი რაოდენობით განსხვავებული სახელები აგრეგაციის მეხსიერებას გაზრდის.

პირველი SQL-აგრეგაციის ვარიანტი ნაკლებ მეხსიერებას იყენებდა, მაგრამ ძველზე ნელი აღმოჩნდა; საბოლოოდ არჩეული ეტაპობრივი წაკითხვა გაზომვის შედეგს ეყრდნობა. გამეორება შესაძლებელია `tests/benchmark.php`-ით, როგორც [ტესტების ინსტრუქციაშია](../tests/README.md).

დამატებული სცენარებით DB suite-მა გაიარა 777 შემოწმება, მათგან 630 არსებული დახურვის რეგრესიებია. ასევე ცალკე ეშვება ფასის, ქვითრის, ოპერაციული დღის, JavaScript ფულისა და მოქმედებების ტესტები.

შემოწმდა:

- ფასდაკლება, სავალდებულო მომსახურება, გატანის გამონაკლისები, ნაღდი/ბარათი/შერეული გადახდა, თეთრამდე დამრგვალება და ძველი ქვითრები.

4. წარმატებული CI-ის შემდეგ `main`-ში გაერთიანება აამოქმედებს არსებულ FTP deploy-ს. ატვირთვა **ატომური არ არის** — დაგეგმეთ ოპერაციების მოკლე პაუზა. შემდეგი გაუმჯობესებაა release დირექტორიის ერთჯერადი გადართვა, თუ ჰოსტინგი მხარს უჭერს.
